# Equivalence Testing and Performance Measurement

Testing provides three kinds of evidence: replay of original Python samples, item-by-item comparison with original C++ execution results, and tests of the shared integer core. `emulated` runs the shared integer core on the CPU and cannot replace CUDA tests on an NVIDIA GPU.

## 1. Original C++ vs. New Executable: Full Iteration History Comparison

First build the C++ version in `../cpp` (see its README); it serves as the baseline. Then, from the `cuda` directory:

```bash
python3 tests/regression.py \
  --baseline ../cpp/build/qbcs \
  --candidate build/qbcs_cuda \
  --backends cpu,emulated \
  --work-dir regression_cpu_emulated
```

On Windows, use `python` and change the executable paths to the actual `.exe` files. All Python test and benchmark tools depend only on the standard library; the original Python project's dependencies are needed only to generate Python replay traces.

Default test matrix:

| Item | Coverage |
|---|---|
| Algorithms | All of ID 1–9 |
| Problems | 3-bit, 5-bit, identity, a single swap with maximum Hamming distance, all distance-1 marker steps |
| Population | N = 4, 5, 10, covering odd and even |
| Update step | Original defaults, `--delta 0`, `--delta 1` |
| Stagnation / memory | `--abc-limit 1`, `--tabu 2` |
| Threads | 1 and 3, with fixed per-trial seeds |
| GPU options | batch = 17; CUDA runs both thread and warp decoders; non-CPU modes add `--check-gpu` |
| Correctness | Every run adds `--verify`, checking the truth table of every evaluated circuit |

That is 9 cases × 9 algorithms. CPU and emulated each have 2 thread settings; emulated runs only the shared scalar core, so it runs thread mode once even if `--gpu-decodes` includes warp. The default `cpu,emulated` gives **324 candidate comparisons** in total, plus 81 reference runs of the original version. Only CUDA mode has 2 × 2 thread/decoder settings, so `--backends cuda` alone also gives 324 candidate comparisons.

Each comparison checks the full CSV, including every generation of every trial and the mean and standard deviation; only `Execution_Time(s)` is excluded. It also compares each trial's final best count, the global minimum, the final statistics, and **the complete global best gate list in the report, including gate order**. The original output does not include each trial's own best gate list, so this CLI test does not claim to compare data that is not output.

### Running on an NVIDIA GPU

```bash
python3 tests/regression.py \
  --baseline ../cpp/build/qbcs \
  --candidate build/qbcs_cuda \
  --backends cuda \
  --gpu-decodes thread,warp \
  --work-dir regression_cuda
```

A failed CUDA run reports an error; the test never falls back to the CPU. `--suite smoke` runs only the first three cases but keeps all 9 algorithms. To also check a population split across multiple batches:

```bash
python3 tests/regression.py \
  --baseline ../cpp/build/qbcs \
  --candidate build/qbcs_cuda \
  --backends cuda --gpu-batch 1 --suite smoke \
  --work-dir regression_cuda_batch1
```

`--work-dir` keeps the full argv, stdout, stderr, CSV, TXT, and `regression_report.json` of every run. `--report PATH` additionally writes a compact JSON report. If any reference or candidate result differs, the program returns a non-zero exit code.

## 2. Seed Consistency for Split Trials / Multiple GPUs

```bash
python3 tests/shard_regression.py \
  --baseline ../cpp/build/qbcs \
  --candidate build/qbcs_cuda --backend emulated --gpu-decode thread \
  --work-dir regression_shards
```

This first compares a 6-trial run of the original and new versions, then splits it with `--trial-offset` into 2 + 1 + 3 trials. After merging, the per-generation history, each trial's best count, and the global best gate list (with the same tie-breaking) must all be identical. N = 5 and GPU batch = 3, which also covers splitting a single population. For GPU testing, change to `--backend cuda`.

## 3. Original Python → C++ Replay

This project keeps the original C++ project's `dump_replay.py` and `replay_test.cpp`. Use the wrapper to generate and replay traces:

```bash
python3 tests/python_replay.py \
  --replay-binary build/replay_test \
  --python-root ../python \
  --output python_replay_results
```

Or replay existing traces:

```bash
python3 tests/python_replay.py --replay-binary build/replay_test \
  --traces /path/to/trace_3_aeqts.txt /path/to/trace_5_qts.txt
```

This test feeds the same four-layer bit samples generated by the original Python into C++, and compares each circuit's gate list, the fitness ranking, and the updated probabilities for AE-QTS/QTS/QEA. The update helper in the replay test comes from the original C++ test copy; by itself it cannot prove that the new production driver updates correctly, so it must be combined with the executable comparison in section 1. Python and C++ use different random number generators, so the same seed cannot be treated as giving the same samples across languages.

## 4. CPU / CUDA Performance Sweep

```bash
python3 tools/benchmark.py --binary build/qbcs_cuda \
  --bits 13 --problem 1 --algorithm 1 \
  --experiments 32 --iterations 200 --neighbors 10 \
  --threads 1,4,16 --gpu-batches 32,128,512 \
  --gpu-decodes thread,warp --out benchmark_13bit
```

You can also add `--baseline ../cpp/build/qbcs` to time the original C++ directly. Without it, the new version's `--backend cpu` is the baseline. Custom problems can use `--tt`, `--tt-file`, or `--tt-sparse`; the units of `--delta` still follow each algorithm's original definition.

By default each setting runs 1 untimed warmup and then 3 measured runs, reporting the median, fastest, and slowest. Timing covers the whole process, including CUDA start-up, data preparation, computation, and output; warmups can warm caches, but every measured run still starts a new process. The benchmark does not enable `--verify` / `--check-gpu`, so per-circuit verification cost is not counted as normal algorithm run time; after each run it still **compares the full convergence history and the global best circuit exactly** against the CPU baseline, and stops immediately on any difference.

Outputs are `benchmark.json`, `benchmark_summary.csv`, and all raw logs, with speedups against the CPU at the same thread count and against **the fastest of all CPU settings tested**. Do not use single-threaded CPU as the only baseline for multithreaded CUDA configurations.

Complete the CUDA correctness regression before formal benchmarking. Record the GPU name, driver, CUDA compiler, CPU model, and test commands, and stop work that noticeably competes for the CPU/GPU on the target machine. Do not report speedups before measuring them. `--backend emulated` is only for testing the benchmark script, and its output is clearly labeled as not a GPU measurement.
